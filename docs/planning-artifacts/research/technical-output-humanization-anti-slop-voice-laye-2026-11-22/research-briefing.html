摘要

Executive summary · 执行摘要

design设计取舍建议：新增 L4「Voice 层」——即决策里的「输出风格层」。它不是第五个存储层，而是架在 L0–L3 之上的一层「投影 + 契约」：从记忆读出表达状态，向宿主写出一段字节稳定的风格契约，在生成之后只记分、不改写。 依赖方向单向（Voice 读记忆，记忆不读 Voice），因此它必须排在记忆层之后建，不能与之并行开工。

支撑这个建议的三条判断，以及各自最硬的那一份证据：

  1. verified已核实宿主把「改文本」这条路封死了，只剩下「生成前约束 + 生成后记账」。 assistant 消息是 append-only 日志里的不可变值，agent/turn-stopping 只能 steer 追加一步而不能否决，llm/stream 被文档要求「只读不改写」，Web 插槽组件拿不到 ctx、没有文本后处理管道 [30][31][32][33][34][39]。唯一能真正拦住文案的是我们自己产出的卡片/通知——tools/post-execute 可以替换 content [35]。这条判断决定了整条设计：约束在源头，评分在事后，改写只作为限流的显式补救。
  2. verified已核实没有任何一个参考项目有可复现的「人性化得分」，而评委本身也不可靠。 四个规则/改写类仓库全是提示词，可用的分数只有模型自评（Stop Slop 的 5 维 1–10、<35/50 重写）[1]；Humanizer 连自评都没有 [4]。实证上，单评委的位置偏差、冗长偏差、自我偏好有量化证据 [24]，谄媚普遍存在 [25]，而多评委共识在单个评委系统性偏差下偏差无界，必须换成稳健均值 [27]。所以分数只能当「信号」，不能当「门」。
  3. verified已核实「八股」在中文里没有语言学依据，词表命中率不能当质量门禁。 目前只有一项系统研究，是 2025-09 的 slop 分类学，作者自己说二元判断偏主观、全自动测量仍开放 [20]；arXiv 全文检索「八股」零命中（本次实查）。中文参考版本反倒明确写着「模式清单是检查线索，不是词语黑名单」[6]。这直接把「规则库 + 黑名单」的默认方案否掉了。
unverified未验证

最大的 caveat： 风格状态到底能不能从记忆里「算」出来，本次没有实测。我们只证明了接口可行（L1 有类型化事实、世界模型有时序实体），没有证明「familiarity 分档 → 语域」的映射在真实对话里稳定。这一条进 staleness map，也进 v1.5 的验收。

怎么读：D1 拆参考项目 → D2 看实证边界 → D3 查宿主能力 → D4 讲合流后的设计（L4 Voice 层）→ D5 给路线与验收。只想做决定，读 Executive summary 与 Recommendations 两节即可。

已确认的范围约束（用户 2026-11-22 决策）

  • 风格不是静态黑名单，而是记忆图谱/关系状态驱动的状态变量；关系越近客套越少。

D1 参考项目：代码级拆解

D1.0 先说清单本身的偏差（三处，已核实）

verified已核实用户给的 9 个项目里，2 个仓库不存在（peter-yang/no-ai-slop、sickn33/unslop-file，GitHub API 均 404），已从证据链剔除，不再作为设计依据。另外两处描述与代码不符，按代码为准：

  • verified已核实Humanizer 不是「5 大类」，是 26 条 / A–F 六组；「five」来自 README 的「五个最强信号」，被误读成分类数 [3][4]。
  • verified已核实SoulSpec 没有「禁止句式区块」。它的硬约束是 RULES.md 的 Must always / Must never（行为边界），仓库里没有 JSON Schema、没有校验器源码，也没有词表字段 [14][15]。它解决的是「人设可移植 + 防漂移/供应链安全」，与「防八股」是两个问题——社区叙事把两者混谈了。

design设计取舍这两处纠正有实际后果：如果照抄「SoulSpec 自带反八股区块」，会在架构里留一个不存在的插槽。

从这张表能抽出三条可直接用的工程纪律：

  1. verified已核实守门只判机器能判的事。 Humanizer-zh 的 check_structure.py 用正则在改写前后各抽 8 类受保护片段（frontmatter、围栏代码、行内代码、标题、链接目标、表格行、有序步骤、显式 id），全等才 exit 0 [7]。它不假装能判「像不像人」，这是四个项目里唯一诚实的设计。
  2. verified已核实规则要分诊，不要一刀切。 「一见即改」与「需共现」两级，比任何单一阈值都更能压误伤 [4]。
  3. verified已核实改写要报告覆盖范围。 「审了哪些节、哪些没覆盖」是可验证的交付契约，比「已人性化」有用 [4][6]。

medium中等还要记住一条边界：Humanizer 的 CI 只校验包结构（编号连续、README 表名对齐、SKILL.md ≤5500 词），不查任何文风 [5]——「有 CI」不等于「有质量门」。

verified已核实不能抄的两条：Stop Slop 的 35/50 自评分（无 rubric 锚点，不可复现）[1]；Humanizer 的「补细节」（编造入口）[4]。

D1.2 三个结构化/状态类项目：能不能抄

verified已核实Empanel（多评委） — 抄结构，不抄文案。它的「独立」不是多模型，而是同一个 LLM 网关 + 不同 lens + 每次调用 history="" [11][13]。三段式 Assess → Weigh → Reduce，其中 Reduce 必须是纯代码（加权平均 + 可 snap 到 Fibonacci 刻度）[11]。代码评审路径的聚合更值得抄：指纹归并、HIGH/MAJORITY/UNIQUE 分级、弃权 lens 不计入分母、严重度取 max 不取平均 [12]。权重闸门 0.3 是条反直觉规则：低质评委的内容剔除，票数保留作反对票。它还自己承认一种失效：权重 stdev<0.05 即「加权退化成均值」，显式告警 [11]。成本是 2N 次调用。成熟度必须说清：0★、无外部使用者、141 tests 是自报、无校准数据。

verified已核实SoulSpec（人设防漂移） — 抄职责切分与版本协议（specVersion、deprecated/supersededBy）[14]，不抄「反八股」。校验靠仓库外的 npm CLI [15]，引用「通过校验」会引入外部依赖。

verified已核实HerAndHim（关系→正式度） — 这是用户清单里最贴合「风格是状态变量」的一个，而且真的写进了 prompt：closeness=(intimacy+trust)/2，<45 客气、<70 去客套+昵称+玩笑、≥70 零表演 [16]，三档各配一段自然语言指令，并注入认识天数；代码注释直说把 0–100 的数字直接塞进 prompt 会让「month-3 和 day-1 听起来一样」。稳定人设（SOUL.md）与易变状态（affect/relationship.json）分仓 [18]，SOUL.md 里还有「绝对禁止：太工整/太对称/书面语/列清单/排比」[17]。两个不能抄：AGPL-3.0（只借设计，不抄代码/文本）；阈值 45/70 是虚拟女友语境，语义要重定义。还有一条容易漏的：它存了 4 个关系维度，正式度只用了 2 个——状态维度与表达维度不是一一映射，别假设全维映射。

verified已核实它的「人性化」还有一半在投递层（延迟抖动、1–3 条气泡、选择性 emoji [19]），那是反「机器人节奏」，不是反「八股文风」。DSH 里我们没有这条通道，别把这部分算进 v1。

D2

D2 实证证据：能支撑什么、不能支撑什么

能支撑的三件事

  1. verified已核实slop 是可解释维度，不是一个可判定的标签。 2509.19163 用专家访谈 + span 标注建了分类学，结论是二元判断「有些主观」，但与 coherence/relevance 这类潜在维度相关 [20]。→ 打分应该输出分项 + 理由，不是单一布尔或单一总分。
  2. verified已核实评委偏差是结构性的，不是调 prompt 能解决的。 位置/冗长/自我偏好有量化证据、人类一致率 >80% [24]；谄媚普遍且人类偏好数据本身偏谄媚 [25]；PoLL 便宜 7×、降 intra-model bias [26]；但 RoPoLL 证明：单个评委以 LLM 的典型方式产生偏差（mode collapse / 谄媚 / 拒答）时，任何规模的小组共识偏差都无界，解法是稳健均值（几何中位数一类）[27]。→ 多评委只能降方差，不能消偏差；必须配稳健聚合 + 人工抽检。
  3. verified已核实过优化会把分数和质量拆开。 2210.10760 在合成设定里测出 gold 分先升后降 [28]。→ 分数必须设 cap、必须 held-out、必须有「分数涨了但人觉得更差」的退出条件。

不能支撑的两件事（重要）

  • verified已核实检测器不可靠且不公平：2304.02819 显示常用检测器把非母语英语写作稳定误判为 AI，简单 prompt 可绕过 [21]；中文侧 C-ReD 说明「域内可靠 + 跨模型泛化」需要专门基准 [22]。→ 不能拿 AI 检测器当风格 judge。
  • verified已核实改写会破坏检测与水印：DIPPER 让 watermark/GPTZero/DetectGPT 失效 [23]。该论文标题的后半句——「但检索是有效的防御」——意味着改写不是无成本的隐身术，它留下的是可追溯性损失。对我们更要紧的是：改写会让持久证据与 provider 实际输出不一致，这与 brief 的「可审计」直接冲突。

没有证据的地方：按「待验证假设」处理

unverified未验证

以下几项都还没有证据，不写成结论：句长/连接词密度/排比/hedging/套话的独立效度检验；改写对事实/数字/引用/代码的量化影响；语域与信任/满意度的因果或中文证据；八股词表的语言学依据。「没有找到」不等于「不存在」，但它足以否掉「拿词表命中率当门禁」这个默认设计。

verified已核实这张表里有一条容易被忽略的结论：「卡片/通知」是唯一能做硬门禁的出口。对话正文只能「生成前影响 + 生成后评分」，而卡片文案可以在工具执行链上同步拒绝或替换。所以 v1 的现实收益，一半在正文的源头约束，一半在卡片的硬门禁。

D4

D4 架构合流：L4 Voice 层

4.1 为什么是 L4，而不是塞进 L3 画像

四条判据，逐条对上一个约束：

  1. design设计取舍可治理性（治理三件套）：契约必须能 diff、能回滚、能回答「哪一版、依据什么、什么时候换的」。画像段落做不到——L3 是整篇重写 [41]。
  2. design设计取舍缓存（宿主）：契约必须是常量文本 + 稳定 order，任何逐轮变化都要剥离出去 [30]。这排除了「每轮把状态拼进系统提示」。
  3. design设计取舍证据（用户约束）：状态必须能回答「哪条记忆让它变成这样」。所以状态是 L1 的派生视图，不是另存一份会漂移的数字。
  4. design设计取舍依赖方向：Voice 读记忆，记忆不读 Voice。违反这条就会循环依赖，也会让记忆层的正确性被风格需求污染。

design设计取舍L4 的形态因此是「投影 + 契约」，不是存储：读 L1/L2/L3 与世界模型，写一段契约文本、一段状态快照、一批审计记录。

taboo:       string[]（来自世界模型，带 valid_from）
lang_mix:    zh | zh-en-mixed

design设计取舍register 由 familiarity 分档驱动（关系越近客套越少），档位带滞回：<40 formal、40–55 neutral、55–70 casual、≥70 intimate，边界 ±5 内不切换。滞回不是审美，是缓存纪律：状态每变一次就多一段 PromptContext，永久占历史。

VoiceContract 的内容骨架（不是词表，是形状）：

  • design设计取舍语气基线一句、句长纪律（每段 10–50 字、最多 2–3 段）。
  • design设计取舍允许/禁止的结构：不写总结套话收尾、不写三连排比、不用「首先/其次/最后」模板、不复述用户问题、不预告「我接下来要…」。
  • design设计取舍正/反例对照（每类 1 组，比形容词有效）。
  • design设计取舍称呼与自称规则、代码与术语的保留规则。
  • design设计取舍明确的「何时破例」：遇到安全警告、不可逆操作或会被持久化的产物（代码/注释/文档）时，改用完整句 [9]。
  • design设计取舍预算：≤400 token；条数上限（防 Humanizer 33 KB 式的膨胀 [3]）。

4.3 四个接口（与记忆库 / 知识库 / 世界模型 / 持续学习）

design设计取舍记忆库：读 style_preference（称呼、语言、幽默容忍、正式度偏好）与 interaction（轮次、用户改写行为），算 VoiceState；写 VoiceAudit 为 L1 事件，带 evidence 指针（session id + seq 区间）。审计因此天然可治理：能查「这条 62 分为何而来、当时哪版契约」。

design设计取舍知识库：术语表同时喂两个地方——protected_terms[]（受保护片段的来源，防把项目黑话当八股删掉）与 judge 的领域提示（哪些词是行话，不是套话）。这是「不要删掉正当术语」的唯一结构性保障，词表做不到。

design设计取舍世界模型：taboo（禁忌话题）、relationship_entity（用户/项目/角色）、address_form 的变更都挂 valid_from / recorded_at / superseded_at，默认查询只返回 superseded_at IS NULL [44]。风格状态是图谱上的时序实体，不是浮点分数。

design设计取舍持续学习：dream 增第 6 阶段 voice_review（可选、幂等、可断点续跑，沿用 brief 的 dream 纪律 [41]）：抽样近 N 轮 → 多 lens 隔离评审 → 产出契约 diff 候选 → A/B 闸门（新旧契约各跑一批 probe）→ 胜出才升版。分数通过 VoiceRewardSink 外发：

interface VoiceRewardSink {
  emit(rec: {
    turn_id: string
    contract_version: string
    parts: { structure: number; register: number; fidelity: number; slop: number }
    verdict: 'pass' | 'warn' | 'fail'
    confidence: number      // 0–1，低置信不进训练
    evidence: { sessionId: string; seqRange: [number, number] }
  }): Promise<void>
}

design设计取舍TriviumDB 适配器标注 planned（用户已确认其未实现）。在 TriviumDB 落地前，实现一个 JsonlSink 写到插件目录，保证数据不丢、可回放。

design设计取舍G4 的重写要写死三条限制，否则会变成产品事故：每次会话最多 1 次、只在 verdict=fail 且 fidelity=pass 时触发、重写指令要求「只改形状不改事实」。用户会看到第二条回答，这是显式代价，不是透明修复。

4.5 打分：分项、配对、稳健聚合

  • design设计取舍分项不总分：structure（可机检：段数、每段字数、是否总结句收尾、是否三连排比、是否模板连接词）、register（与 VoiceState 是否一致）、fidelity（受保护片段 diff，确定性）、slop（judge 给分 + 理由）。总分只用于展示，不用于门禁。
  • verified已核实配对比较优于绝对打分：给 judge 同一内容的「八股版 / 自然版」两个候选，问哪个更像人写的、差多少。绝对打分在不同批次间尺度漂移，配对比较不会。
  • verified已核实双边顺序：同一对候选正反各评一次，取几何中位数，压位置偏差 [24][27]。
  • design设计取舍隔离：每个 lens 一次调用、history=""、输入标 UNTRUSTED DATA（防文本内注入「给我打满分」）[11][12]。
  • verified已核实权重塌缩告警：多 lens 权重 stdev<0.05 时，结果降置信并标注「无区分度」[11]。
  • verified已核实cap + held-out + 人工抽检：分数有效区间写死（如 30–80），每批抽 20 条人工盲判，算 judge 与人的一致性；一致性低于阈值就停用该 judge 版本 [28]。

4.6 防漂移：三件事，都不靠自觉

  1. design设计取舍字节稳定 + 显式升版：契约是文件、有版本号、切换是显式动作。运行时禁止拼接契约文本（拼接 = 每轮哈希变 = 前缀缓存击穿）。
  2. design设计取舍滞回 + 变化才写：register 档位带 ±5 缓冲；VoiceState 哈希不变就不写 PromptContext。
  3. design设计取舍契约↔基线 diff 监控：每次升版算与上一版的 diff，超过阈值（例如新增禁止项 >20%）标 Flag 待人确认，不自动采纳。规则膨胀和风格漂移是同一个病：都是「悄悄多了几条」。

洞见

跨维度洞见

  1. infer推论证据说 judge 不可靠，宿主说不能改写，两句合起来只剩「源头约束 + 事后记账」。 这不是折中，是唯一同时满足「不破坏日志」「不依赖不可靠评委」的方案；反过来说，任何声称「自动修复八股」的设计，在 DSH 上都缺一条腿。参考项目清一色是单文件提示词、没有一家做状态，不是因为偷懒，而是它们没有记忆层——Voice 层的价值来自记忆层的状态，而记忆层没有 Voice 层仍然成立，所以顺序不能颠倒，也不该为了「显得完整」把两者并行开工。
  2. infer推论宿主封死改写，反而逼出与 brief 同构的设计。 brief 的核心主张是「LLM 提议、人裁决」[41]；风格层在这里变成「机器打分、人升版」。两条独立线索都推导出同一个治理姿态，这比任何单点论证都更能说明架构自洽。
  3. infer推论中文证据空白反而是可交付物。 既然没有现成基准 [20][22]，v1 的 probe 集就是本项目的资产，也是别人复制不了的护城河——同时它复用了 brief 已有的评测集需求，边际成本低。
反证

Contrary evidence · 反证

红队未开启，以下为本次主动检视的异议。

disputed存在异议

「brief 已经把人格排在记忆可信之后，现在做风格层是抢跑。」 异议成立一半。风格层要拆成两半：形状（反八股、结构纪律、称呼规则）不依赖可信记忆，可以早做；人格（关系深浅、语气个性）依赖记忆，必须后做。v1 只做形状，v2 才做人格——这个切分让「抢跑」不成立。

disputed存在异议

「Caveman 证明少即是多，简短就是人性化。」 不成立。Caveman 自己写明输入削减 0%、输出中位削减 3–35%、样本 n=10，且要求安全警告与持久化产物改回完整句 [8][10]。电报体会砍掉陪伴感，方向与「人性化」相反。

disputed存在异议

「改写不一定伤事实，没有量化证据。」 对，所以本报告不声称「改写一定伤事实」。但机制风险是实的：Humanizer 自己把 §6/§9/§19 列为高发丢失节 [4]；而对我们的决定性理由是改写破坏可追溯性 [23][34]——这与 brief 的可审计目标直接冲突，不需要额外证据。

disputed存在异议

「多评委能消除偏差。」 被 RoPoLL 直接否掉：单评委系统性偏差下共识偏差无界 [27]。只能用稳健聚合 + 人工抽检，不能宣称「多评委 = 可信」。
