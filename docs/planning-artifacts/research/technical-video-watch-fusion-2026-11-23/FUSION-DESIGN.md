# 看视频融合方案设计

## 0. 结论先行

**帧数不设上限；上限只加在「同一时刻上下文里装多少」。**

这个方向我走错过一次，记在这里免得再走：初版为了让「2 小时与 10 分钟同价」，给帧数设了 36 帧硬顶，代价是长视频盲区 7.5 分钟。这是把「看得全」当成了可牺牲项。用户当时的判断是：分析如果是垃圾，省下的 token 只是把钱扔进碎纸机（m873）。那句话是对的。

改后的成本方程：

```
总视觉成本   ≈ ⌈总帧数 / 每张格数⌉ × 每张图版单价 + 精读张数 × 裁切单价
同时可见成本 ≈ 单块图版数 × 每张图版单价        ← 这才是限制注意力的那个量
```

两句话：

- **帧数由信息密度决定，不由预算决定。** 静止讲解段可以 5 分钟一帧，操作演示段可以 2 秒一帧；全片覆盖率必须 ≥ 95%（任意 60s 窗口至少一帧），达不到就加帧，不封顶。
- **上限只加在同时可见的图版数上（默认 3 张 ≈ 1,038 token）。** 帧全部落盘成证据库，按块分批进上下文；一块读完写一份结构化笔记，图像丢弃。总成本随信息量线性增长——这是视频长度决定的，省不掉；但常驻上下文是常数。

四条主线：

1. **先量测，再采样**：ffmpeg 一遍扫全片（现实测 **21–26× 实时**：136s 片 6.6s、585s 片 27.2s；早期用 60s 合成片测得的 7× 是乐观值），加上弹幕时间轴，得到 0 token 的 `timeline.json`，用它决定看哪里、看多密。
2. **拼图省的是单帧单价，不是覆盖范围**：一张图放 9 帧与放 4 帧同价，所以拼图让你在同样的钱里多看几倍的帧——不是让你少看。这是本轮唯一允许拿来做成本优化的一层。
3. **图版只定位，读字回原图**：拼图里读出来的字一律不采信；要读字就裁原分辨率，620×170 的裁切约 64 token，而整帧 559。
4. **分批阅读，笔记过手**：图像只在它那一块的处理期间存在，出来后只有笔记留下。全局观后感从笔记合成，不回放图像。

## 1. 成本结构：实测与口径

### 1.1 本机实测（决定优化着力点）

| 环节 | 实测 | 结论 |
| --- | --- | --- |
| 逐帧启动 ffmpeg（现做法） | 106 ms/帧 | 500 帧 = 53s 纯进程开销 |
| 单遍 `fps`/`select` 滤镜 | 6 ms/帧 | 快 17.7×，一样能落盘 |
| `scdet` 全片扫描 | 60s 片 433 ms | 场景检测≈免费 |
| 全片量测（`scdet`+`freezedetect`+`signalstats`+`silencedetect`，真实素材） | 136s→6.6s、301s→14.0s、585s→27.2s | **21–26× 实时**，2h 片约 5 分钟；见 §1.3 |
| 1280×720 整帧送模型 | ≈559 token | 唯一真正的开销 |
| 620×170 裁切送模型 | ≈64 token | 读字成本是整帧的 1/8.7 |
| 一张 756px 9 格图版 | ≈346 token（摊到 38 token/帧） | 比整帧便宜 14.7× |

抽帧与场景检测已经便宜到可以忽略；**唯一值得优化的就是「送进模型的东西」**。这不是算力问题，是排版问题。

### 1.2 token 口径（三个项目相互印证）

| 来源 | 公式 | 校验 |
| --- | --- | --- |
| sense-now `src/runner.js:26-32` | 像素 ÷ 1650 | 800×450=218、1280×720=559、1600×900=872 |
| see-now `src/tokens.js:1-35` | 14px patch 对齐 → 42px 格 → `rows×(cols+1)+2`，单图≤1024 | 798×462=222、1050×630=392、1260×756=560、1596×924=860 |
| video-watch-plus `vendor/vw.py:51-53` | 756² ÷ 1650 ≈ 346 | 9/16/25/36 格同价 |

三套口径误差 ≤5%，可视为同一公式。**本方案统一用「像素 ÷ 1650」做预算，用 see-now 的对齐公式做核对**（宽度按 42px 对齐能省 11~24 token/张，300 张就是 3~7K）。

关键推论：**一张图版的价格只由画布像素决定，与里面塞了几帧无关**。所以格数选择不是一个成本决策，而是一个**清晰度决策**：

| 画布 756px | 格数 | 单格边长 | 能看清什么 | 摊到每帧 |
| --- | --- | --- | --- | --- |
| 3×3 | 9 | 250px | 场景类型、构图、人脸、UI 布局 | 38 token |
| 4×4 | 16 | 187px | 同上但更粗糙 | 22 token |
| 5×5 | 25 | 149px | 只能判「是不是同一场景」 | 14 token |
| 6×6 | 36 | 124px | 只适合做缩略导航 | 10 token |

**图版从不用于读字**——250px 的格子里一行中文不到 10px 高。这是 video-watch-plus 用两次翻车换来的结论（`SKILL.md:22-27`：在图版里「读」出了画面上不存在的字）。

「现做法」= 每 15 秒一帧、整帧送模型、全部常驻（`scripts/plan_densities.py:22` 的 `normal 15` + 559 token/帧）。

四个能直接引用的结论：

1. **token 口径对得上**：23,182 ÷ 577 = **40.2 token/帧**，理论值 346/9 = 38.4，偏差 5%。§1.2 的公式在这批真实素材上成立，预算可以按它算。
2. **成本按分钟算是 355–1,158 token/分钟（中位 662），帧数是 9–29 帧/分钟（中位 16）。体裁差异远大于时长差异**——快剪发布会是短剧的 3.3 倍/分钟。任何「每分钟固定抽 N 帧」的预算都会在这两端错，这也是 §6 换成区间表的理由。
3. **切点锚定是帧数的主要来源**：快剪发布会 322s 里有 160 个检出切点、154 帧（≈每镜头一帧）；短剧 585s 只有 63 个切点、88 帧。所以「帧数」实际是「镜头数」的代理，不是我们主动选的密度。
4. **去重在这批素材上只丢掉 6.3%**（616→577）。因为帧已经被摊开，dHash 主要在合并「同一镜头内的相邻帧」。合成素材里重复段落多，才会出现 157→61 这种折叠（见 §1.4）。

### 1.4 合成素材：基准真值与长度缩放

真实素材没有标准答案，所以另建两支已知答案的合成片：

- **切点召回（`SYNTHCUTS1`，120s，7 段，硬切已知在 10 / 25 / 40 / 41.5 / 70 / 100 秒）**：检出 6 个切点，**召回 6/6**；41.5s 落进 41s 桶（5s 量测窗口的时间分辨率上限，不是漏检）。去重后 17 帧剩 6 帧，每个镜头各留一帧，1.5s 的绿色过场也被正确并进相邻镜头。
- **长度缩放（`SYNTHLONG1`，1200s，10 段重复串接）**：量测 29.2s（41× 实时）、规划 157 帧、去重 61 帧、8 张图版、2,768 token、覆盖 100%，基线 45,279 token（16.4×）。重复段落被正确折叠成每镜头一帧。

合成素材暴露了两条只有它能暴露的边界，都已写进设计：

- **纯色/平坦画面 dHash 失效**：4 个不同纯色被算成同一个哈希（灰度行内梯度全零）。真实视频里对应黑场、纯色底字幕卡。黑场没信息，丢掉是对的；**字幕卡有字，不能丢**——所以去重之后要再加一道「含字幕带的帧一律放行」。
- **画面持续变化但整体结构不变的镜头会被折叠**（testsrc2 那种）。9×8 灰度的 dHash 只有 72 位，对局部变化不敏感，这是分辨率决定的不是 bug。需要看清的细节靠「图版里发现异常再回原图精读」补，不能指望哈希。

## 2. 五级阶梯

每一级都是「便宜的先做，贵的后做，能不做就不做」。上一级的产出决定下一级要不要跑。

### V0 — 量测（0 token，全片）

一遍 ffmpeg 走完，不出图、不进模型：

```
ffmpeg -i in.mp4 -vf scdet=t=10,freezedetect=n=-60dB:d=2,tblend=difference,signalstats,metadata=print -an analysis_v.txt
ffmpeg -i in.mp4 -af silencedetect=n=-35dB:d=1 -f null - 2> analysis_a.txt
```

逐秒聚合出 `timeline.json`：`motion`(YAVG 均值)、`spike`(YMAX)、`cut`(scd.score≥10)、`freeze`、`silence`。同时落 `social.json`（弹幕带秒级时间轴 + 30s 密度桶）。

**实测**：136s 片 6.6s、301s 片 14.0s、585s 片 27.2s（21–26× 实时），2h 片约 5 分钟；合成 1200s 片 29.2s（41× 实时，画面简单解码更快）。相比「先按预估密度抽 120 帧再看」，量测这一步便宜 4 个数量级。

### V1 — 文本（≈0 视觉 token）

优先级固定六级，前一级拿不到才降一级：CC 字幕 → 外挂 SRT/VTT/ASS → 内嵌文本轨 → 弹幕高频关键词 → 本地 ASR（Qwen3-ASR）→ 画面 OCR（本项目暂不做）。

三条纪律（借 sense-now 与 streamvision）：
- **ASR 需授权**：`asr.mode = off|fallback|full`，默认 `fallback`（只在字幕缺口且缺口 > 全片 20% 时跑）；`off` 时零调用。
- **文本去抖**：重叠窗口产生的重复段，按 bigram Jaccard ≥0.85 且两次出现间隔 ≥1200ms 合并，落盘用第一次的版本（streamvision `lib/text.js:32-33`）。
- **幻觉两判据**：VAD 无输出前提下，① 互不重叠窗口输出完全相同文本；② `no_speech ≥ 0.4` → 标 `ASR_SUSPECT`，该段不进结论。

产出 `transcript.json`（带时间轴）+ `topics.json`（LLM 读一遍转写给出话题段与密度建议，这是现技能已有的能力，保留）。

### V2 — 密度驱动分块采样（帧数不设上限）

**不是「骨架 16 帧 + 事件 6 处」，而是「逐段决定该看多密」。** 这一步是全案唯一按信息量花钱、不按预算花钱的地方。

**① 分块**：块边界优先落在自然断点上——低运动（`motion ≤ p20`）且有停顿（`silence ≥ 1.5s`）的时刻；最长不超过 8 分钟，最短 90 秒；找不到自然断点时按 5 分钟硬切。相邻块共享 20s 重叠，重叠处的发言按时间中点归属（sense-now `src/video-index/chunk-plan.js:5-6,60-107`）。

**② 密度打分**（每 5s 一个窗口，全部来自 V0/V1，0 视觉 token）：

```
dens = 0.35·norm(motion) + 0.25·norm(|ΔYMAX|) + 0.15·cut数
     + 0.15·弹幕条数(p90 归一) + 0.10·字幕字数
```

权重按块类型可调：静止讲解块由字幕字数与弹幕主导（信息在话里），操作演示块由 motion 与 cut 主导（信息在画面里），直播/游戏块由 motion 与弹幕主导。这不是猜的——切成三类之后再按 `dens` 的分位数定档。

**③ 档位与帧数**：`dens` 的五分位 → 五档间隔。

| 档 | 间隔 | 典型内容 |
| --- | --- | --- |
| 极稀疏 | 300s | 纯静态课件、长时间黑屏/标题 |
| 稀疏 | 60s | 口播、访谈 |
| 常规 | 15s | 教程、测评 |
| 密集 | 5s | 操作演示、代码输入 |
| 极密 | 2s | 快速切换、字幕轰炸、游戏战斗 |

每块帧数 = ⌈块时长 / 该块间隔⌉，**不设上限**。一块 8 分钟的极密段可以出 240 帧，那就是 27 张图版——该花就花。

**④ 去重**：对候选帧算 dHash（`rawvideo` 读出，不落中间图），汉明距离 < 6 丢弃。三条必须同时成立才许丢：

- **跨距 ≤ 50s**：不设跨距，100 秒后重新出现的同一场景会被当成重复帧丢掉。实测就是这样打穿了覆盖率——短剧那支一度只剩 92.9%、留下 101.8s 的洞。
- **丢了不会有 >55s 的缺口**：只看「与上一张保留帧的距离」不够，连续丢弃会累积成 2× 跨距。判据要显式看「丢下去之后到下一个保留帧有多远」。
- **不含字幕带**：平坦底色上的字幕卡会被 dHash 判成纯色（合成素材已复现），这类帧一律放行，交给 V3 去 OCR 或精读。

实测去重收益不大（六支素材 616→577，6.3%），因为候选帧本来就被摊开了；它的真正作用是在重复段落（片头片尾、循环演示、十段重复的合成片）上把帧数压下来。

**⑤ 逐块交付**：每块抽出的帧拼成 9 格图版，一张一张进上下文；**同时可见 ≤ 3 张**（≈1,038 token）。读完该块必须产出一份结构化笔记：时间轴、关键事实、证据帧号、不确定项。笔记落盘后，图像丢弃。

**⑥ 覆盖率复核**：审计统计「任意 60s 窗口至少有 1 帧」的比例，低于 95% 就对该段**加密度重跑**。加帧永远优先于降帧——这是本方案与所有「按预算砍帧」方案的分野。

产出：`shotlist.json`（每帧带 reason 与所属块）+ 每块 `notes/<chunk>.md` + `manifest.json`（第几行几列 = 第几秒，行列编号烧在格子上）。

### V3 — 定点精读（按需，64 token/张）

只有三种情况才触发：

| 触发 | 手段 | 单价 |
| --- | --- | --- |
| 要读字（界面、代码、公式、字幕模糊段） | `--region` 裁切 620×170 放大 2× | ≈64 token |
| 要看清动作（操作演示的 0.1–0.5s 级） | 同区域按帧号纵排 3–5 帧 | ≈100 token |
| 要确认画面细节（人物/物体/颜色） | 该时刻原帧，1280 宽 | ≈559 token |

**预算闸**：每个视频最多 12 张精读图（≈800 token），超了就写进产出「已省略 N 处精读」。

### V4 — 反思补抽（≤3 窗口，需确认）

触发条件不能是「再看看」，必须是**具体缺口**：

- 审计码命中（§5）
- 模型明确写出的不确定点（「03:12 之后的画面没看到」）
- 覆盖率 < 0.7 的时间段

执行前必须给出 `planHash`（sha256 前 24 位）+ 参数白名单 + 窗口数，用户或上层确认后才跑；`maxRefineWindows 3`，二次总成本 ≤ 首轮（sense-now `src/video-index/analysis-policy.js:13-29`）。

## 3. 五条定律

1. **先量测后采样**：能用 ffmpeg/本地计算/弹幕算出来的，绝不进模型。V0 的 433ms 换掉的是 67K token。
2. **拼图省的是单帧单价，不是覆盖范围**：一张图放 9 帧与放 4 帧同价。所以拼图让你在同样的钱里多看几倍帧——不是让你少看。
3. **图版只定位，读字回原图**：拼图里的文字一律不采信，违反这条会直接产出幻觉（vwp 实测两次）。
4. **覆盖率是硬指标，不是可选项**：任意 60s 窗口至少一帧，全局 ≥95%。达不到就加帧。**只有「同时可见」可以被预算约束，覆盖范围不行。**
5. **分批阅读，笔记过手**：图像只在它那一块处理期间存在，出块即丢，留下的是结构化笔记。全局结论从笔记合成。

第 4、5 条合起来，是对「注意力是有限资源」那句话的回答：**限制的应该是同时压在注意力上的量，不是看过多少**。承认看不到仍然比假装看到有用（所以盲区要报数），但「为了省钱少看」不在允许的取舍里。

## 4. 弹幕：第四类事件源（本方案的增量）

本机 `fetch_social.py` 拿到的每条弹幕都带秒级时间轴（`scripts/fetch_social.py:69-81` 保留 `t` 字段），这是四个参考项目都没有的免费信号；模块侧由 `src/watch/social.ts` 复刻同一口径（5s 分桶）。

用法：

1. **密度曲线当注意力先验**：按 5s 分桶，取 p90 以上的桶作为候选事件点。观众在哪里集中发弹幕，哪里大概率有内容（笑点、翻车、结论、名场面）。零视觉成本覆盖全片。
2. **关键词当日志**：弹幕里的「这里写错了」「03:12 那个」「求源码」直接当精读线索，去对应时刻裁切读字。
3. **权重上限，不再是配额**：弹幕在 `dens` 公式里占 0.15，且该权重封顶 0.3；同时剔除首尾各 30s（片头刷屏、片尾催更没有信息量）。这样它能把某一段的密度抬高，但抬不到「只因为弹幕热闹就多看三十帧」的程度。

风险与处置：弹幕峰值常与画面变化不重合（笑点可能是口播）→ 只作为**并列源**而非主源；非 B 站视频无弹幕 → 该源静默跳过，不影响其他三类。

## 5. 覆盖与可追溯

### 5.1 覆盖率三分离（借 sense-now `coverage.js:78-115`）

`scan`（扫了多少时间轴）/ `text`（多少时间有文本证据）/ `speech`（多少时间有语音）分开算，**截断时不得把未扫区域算成已扫**。状态：`text ≥ 0.7 → good`、`≥ 0.3 → partial`、否则 `poor`。

**本方案在这一组之上加第四条：`frame`（帧覆盖）**——按时长切成 60s 窗口，统计「至少有一帧」的窗口占比，目标 ≥ 0.95。这一条是「看了多少」的唯一硬指标，也是 G-w-9 的被测对象。前三条回答「有没有文本证据」，这一条回答「有没有睁眼」。

### 5.2 审计码

| 码 | 触发 | 后果 |
| --- | --- | --- |
| `WATCH_FRONT_BIAS` | 事件点全部落在前 20% | 强制从后 80% 补 2 处 |
| `WATCH_BLIND_ZONE` | 存在连续无帧区间 > 90s，或某 60s 窗口零帧 | 产出里写明盲区秒数与位置，并触发加密度重跑 |
| `WATCH_SUBTITLE_GAPS` | 有语音但无文本的段落 > 15% | 提示可开 ASR |
| `WATCH_SPEECH_WITHOUT_TEXT` | 检测到语音但转写为空 | 标 `ASR_MISS`，该段不进结论 |
| `WATCH_SHEET_READ` | 结论引用了图版里的文字 | **硬失败**，必须回原图重读 |
| `WATCH_DANMAKU_ONLY` | 某结论只有弹幕证据、无画面/字幕证据 | 标「据弹幕推测」 |
| `WATCH_TIME_REVERSE` | 时间轴出现倒序 | 硬失败 |

### 5.3 不写假 ready（借 sense-now `schema.js:7-9`）

七个能力态：`disabled / skipped / unavailable / pending / degraded / ready`。抽帧没落盘就是 `degraded`；OCR 未配置就是 `unavailable`；不做实时就是 `disabled`。任何产出都带这七个态的当前值——**用户一眼能看到哪一块没做**。

## 6. 预算表（帧数不封顶，成本随信息量走）

下表按 §1.3 实测的每分钟速率外推（9–29 帧/分钟、355–1,158 token/分钟，中位 16 帧与 662 token）。外推用区间，不给单点，因为体裁差异比时长差异大。

| 时长 | 帧数 | 图版 | 总视觉 token | 同时可见 | 精读额度 | 覆盖率目标 |
| --- | --- | --- | --- | --- | --- | --- |
| 10 min | 90–290 | 10–33 | 3.5–11.4K | ≤3 张 ≈1,038 | ≤8 张 | ≥95% |
| 30 min | 270–870 | 30–97 | 10.4–33.6K | ≤3 张 ≈1,038 | ≤12 张 | ≥95% |
| 2 h | 1,080–3,480 | 120–387 | 41.5–134K | ≤3 张 ≈1,038 | ≤20 张 | ≥95% |
| 3 h | 1,620–5,220 | 180–580 | 62–200K | ≤3 张 ≈1,038 | ≤24 张 | ≥95% |

区间的两端来自实测：下限是「口播/短剧型」（≈9 帧/分钟），上限是「每 2 秒一个切点的快剪」（≈29 帧/分钟，见 §1.3 的快剪发布会）。**这不是预算，是预期；实际由切点数与每块的 `dens` 决定，算出来几帧就是几帧。**

比上一版（10min 60–120 帧、2h 18.6–34.6K）高约 2.5 倍。上一版的错在于假设「真实视频很少全片密集」——实测的快剪素材就是每 2 秒一个镜头，它的帧数由镜头数决定，不由我们决定。这个偏差必须写进来，否则预算是自我安慰。

对照现状：30 分钟视频按 `normal 15s` 抽 = 120 帧 × 559 = **67K 视觉 token，且全部常驻上下文**。新方案在同样的片子上看 **270–870 帧**（是现状的 2–7 倍），花 **10.4–33.6K**（是现状的 1/2 到 1/6.4），而任一时刻压在注意力上的只有 **1K**（现状 67K）。**帧数变得更多是设计目标，不是副作用**——同样的钱买了一倍到数倍的覆盖率。

**极端情况不砍帧**：若 2 小时片整片接近快剪上限（每 2 秒一镜头，实测 28.6 帧/分钟），会到 3,400 帧以上、380 张图版、约 132K 视觉 token；3 小时会到 5,200 帧、200K。这时候不许偷偷降密度，而是三选一并报数给用户：① 分多轮会话读（每轮 8 块，笔记累积）；② 只对最需精读的块提密度；③ 接受这个成本。**先把数摆出来，再让人选。**

模式（skim / normal / deep）不再是帧预算，而是**精读额度与笔记深度**的档位：skim 只出块级一句话，normal 出结构化笔记，deep 要求每块附带「可复现步骤」或「事件因果链」。帧密度全部由信息量决定，三档一致。

## 8. 落地形态：插件内的一个 TS 模块（未来迭代）

**不是技能里的 Python 脚本。** 采样、拼图、预算、审计都是插件的模块，用 TypeScript 写在本仓库 `src/` 下，与记忆/人格/治理模块同进程、同一套配置与审计。技能只保留它擅长的部分：下载、结果编排、观后感与归档。

### 8.1 模块划分

| 模块 | 职责 | 文件（拟定） | 依赖 |
| --- | --- | --- | --- |
| probe | 一遍 ffmpeg 量测 → `Timeline`（cut/spike/motion/freeze/silence） | `src/watch/probe.ts` | `src/seams/ffmpeg.ts` |
| social | 弹幕密度桶（5s）+ p90 峰值 + 关键词时刻 | `src/watch/social.ts` | 宿主 fetch / 既有抓取 |
| shotlist | 分块 + `dens` 打分 + 档位 → `Shotlist`（每帧带 reason、所属块、`coverage`、`tokens_est`；**无帧数上限**） | `src/watch/shotlist.ts` | probe / social |
| notes | 块笔记的落盘路径与 schema（内容由模型写，模块只管边界与校验） | `src/watch/notes.ts` | — |
| sheets | 抽帧 → 9 格 756px 图版 PNG + `manifest.json` | `src/watch/sheets.ts` | seam + `node:zlib` |
| frames | 精读：单帧裁切、0.1s 序列条 | `src/watch/frames.ts` | seam |
| budget | token 估算（像素÷1650、42px 对齐）与闸门 | `src/watch/budget.ts` | — |
| audit | 覆盖率（含「任意 60s 窗口至少一帧」）+ 七个审计码 + 七态 | `src/watch/audit.ts` | — |

接缝按 AD-15 的层依赖规矩放：`src/seams/ffmpeg.ts` 只导出 `spawnFfmpeg(args): AsyncIterable<Buffer>` 与 `probe(path)`，测试里替换成假实现即可，`src/watch/*` 不直接 `import` `node:child_process`。

### 8.2 运行边界

- **ffmpeg / ffprobe / yt-dlp / ASR 都是外部进程**，由 seam 以 `spawn` 调起，模块本身是纯 TS、无原生依赖。
- **不用 sharp / jimp / cv2 / imagehash**：PNG 编码用 `node:zlib` 自写（see-now 的 `src/png.js` 就是这么做的），感知哈希对 `rawvideo` 管道读出的像素直接算，不落中间图。
- **ASR 仍是本机 Qwen3-ASR venv**（`D:\dsh-asr\venv\Scripts\python.exe`），由 seam 以子进程调用；它不进入模块的依赖图，模块只消费它的 JSON 输出。
- **不做整片流式解码**：全片扫描只读 ffmpeg 的 `metadata=print` 文本日志（0 解码）；只有选中的帧才真正解码算 dHash。see-now 连续流 `rawvideo` 是因为它服务实时画面，我们是一次性观看，没有这个必要——2 小时片若按 12fps 全片流式解码要过 90GB 管道。注意这条限制的是「解码方式」，不是「看多少帧」：帧数按信息密度取，多到 3,000 帧也只是 3,000 次定点 seek，实测 6ms/帧。

| G-w-6 | ASR 克制 | 无字幕时默认不跑 ASR；跑了的段带 `ASR_SUSPECT` 判据结果 |
| G-w-7 | 成本可预知 | `watch_plan` 输出的 `tokens_est` 与实际用量偏差 ≤ 15% |
| G-w-8 | 质量不降 | 同一批 5 个视频，融合版与现版观后感在「关键结论是否遗漏」上人工对照，不劣于现版 |

| G-w-10 | 密度真的在起作用 | 帧间距与 `dens` 的 Spearman 秩相关绝对值 **> 0.45**（只统计非切点锚帧）。原定 0.6 在六支实测里有两支不达标，原因是锚帧按内容边界放置、与 `dens` 无关；把锚帧算进去测不出「密度是否在起作用」 |
| G-w-11 | 笔记过手 | 每块都有 `notes/<chunk>.md`；全局结论的断言能指回笔记，而不是指回图像 |
| G-w-12 | 去重不许自己作恶 | 去重前后覆盖率都 ≥ 95%，且去重造成的最大缺口 ≤ 55s；含字幕带的帧不得被去重丢弃 |

## 12. 权重的实测：不敏感的是权重，敏感的是档位

`dens` 公式里的权重不是从别处抄来的（四个参考项目都没有「信息密度」这个量）。本轮在三支不同体裁的片子上各扫了六个变体（`node watchlab.mjs sweep <BV>`），结果和预期不一样：

| 变体 | 快剪发布会 5.4min | 短剧 9.8min | 单人口播 9.3min |
| --- | --- | --- | --- |
| base（弹幕 0.15 / hamming 6 / 块 480s） | 154 帧 / 6,228 | 88 / 3,460 | 167 / 6,574 |
| 弹幕权重 0 | 154 / 6,228 | 89 / 3,460 | 163 / 6,574 |
| 弹幕权重 0.30 | 155 / 6,228 | 89 / 3,460 | 163 / 6,574 |
| hamming 4 | 159 / 6,228 | 91 / 3,806 | 170 / 6,920 |
| hamming 10 | 151 / 5,882 | 79 / 3,114 | 156 / 6,228 |
| 块 300s | 154 / 6,228 | 88 / 3,806 | 167 / 6,574 |

三条结论，第二条是这轮最值钱的发现：

1. **弹幕权重 0 / 0.15 / 0.30 对 token 毫无影响**（三支视频九个组合，token 完全不变），帧数最多差 7 帧，ρ 变化 ±0.09。
2. **原因不是「弹幕没用」，而是档位是个五分位映射**：`dens` 只有穿过分位边界才会换档，权重微调几乎不越界；再叠加切点锚帧已经占掉大部分帧位。**真正敏感的旋钮不是权重，是档位边界（2/5/15/60/300 这五个数）和切点策略**——标定工作应该花在后者，权重只需保证「不乱序」。
3. **hamming 是唯一能明显改变成本的参数**：4→10 在短剧上 3,806→3,114（−18%）、口播 6,920→6,228（−10%）。但 hamming 10 开始吞掉「同场景不同机位」，且必须服从 G-w-12 的缺口约束。

由此修正弹幕的用法：它不适合当 `dens` 的全局权重，更适合**只在已判为热点的时间段里局部提密**（技能现有的 `hot_spans` 30s 桶就是这个思路）。§4 的「权重 0.15、封顶 0.3」保留为默认值，但不再当主要杠杆。

## 13. 本轮实测带来的设计修订

| # | 修订前的说法 | 实测发现 | 改成 |
| --- | --- | --- | --- |
| 1 | 量测 ≈7× 实时（60s 合成片） | 真实素材 21–26× 实时，2h 片约 5 分钟 | §0 / §1.1 / V0 全部改为实测值 |
| 2 | 10min 60–120 帧、2h 18.6–34.6K token | 实测 9–29 帧/分钟、355–1,158 token/分钟 | §6 换成区间表，整体上调约 2.5× |
| 3 | 去重只与上一张保留帧比较 | 短剧留下 101.8s 空洞、覆盖 92.9%；hamming 10 时再次复现 | 跨距 ≤50s + 缺口 ≤55s + 字幕带放行（V2 ④），并加 G-w-12 |
| 4 | G-w-10 要求 ρ > 0.6 | 六支素材里有 2 支是 0.48 / 0.54，原因是锚帧按内容边界放置、与密度无关 | 阈值 0.45 且只统计非锚帧 |
| 5 | 权重是主要标定对象 | 弹幕权重对 token 零影响，档位边界才敏感 | §12 改为「权重只求不乱序，标定花在档位与切点」 |

这五条都是同一类错误：拿合成素材或直觉当基准，没在真实素材上验。记录在此，避免下一轮重犯。
