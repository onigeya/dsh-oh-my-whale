## 决策要回答的三个问题

1. 上下文治理在 DSH 里到底治什么（成本结构是什么）？
2. 三个实现各自把「决定权」放在哪——模型、代码、还是阈值——代价分别是什么？
3. 我们的记忆模块与人格模块已经占用了注入出口与证据指针，上下文治理要怎么接，才不产生第二套真相？

## 成本结构：三个成本，不是一

> **2026-11-23 修正（用户反馈）**：本节最初把注意力写成了「token 的副产品」。这是错的——注意力是目标，下面三项都是为它服务的预算与底线。bili §6.4 专门有一节讲「注意力留在可靠区间内」，argp 的「焦点轮保护」也是同一件事；本报告当时把两者都归入了「质量」而没有单列。设计文档已按「注意力优先」重写（AD-42 … AD-45），本节的三个成本应读作：**目标之下的三项约束**。

任何上下文治理都在三个互相拉扯的量之间做交换，而不是只做「省 token」：

| 量 | 为什么会疼 | 谁来支付 |
| --- | --- | --- |
| 窗口占用 | 超过模型窗口即硬失败；接近窗口时注意力质量下降 | 每轮输入 token |
| 前缀缓存 | 任何对已发送前缀的改写都会让服务商 KV 缓存失效，缓存命中从 97% 掉到 0 | 下一次请求全量重算 |
| 可追溯性 | 有损摘要丢掉的细节再也拿不回来（除非另存了原文） | 任务质量、事后审计 |

三个实现的分歧，本质是对这三个成本的排序不同：weave 优先可追溯性，argp 优先缓存与确定性，billion-context 优先长会话容量。

## 三个实现速览

| 维度 | compaction-weave | dsh-argp | billion-context |
| --- | --- | --- | --- |
| 谁会调用模型 | 摘要时（唯一 LLM 步骤） | 只在「散文浓缩」双闸都过线时 | 每次折叠（模型自己决定折哪段） |
| 压缩对象 | 工具输出先折叠，再折对话区间 | 只剪工具结果 R | 已消费的增量（消息区间/块） |
| 决定权 | 代码（审计后接受/拒绝摘要） | 代码（确定性规则） | 模型（时机、范围、内容、拒绝权） |
| 原文去哪 | 本地归档 + history_* 工具回查 | 宿主 append-only 日志 + 标签/关键词召回 | 块谱系 + decompress / decompress-to-file |
| 失败方向 | 摘要不合格就不替换，保留原历史 | 剪枝失败保持原文 | 拒绝折叠 = 质量阀，不是失败 |
| 缓存纪律 | 同路由原样前缀、增量压缩只折最新检查点之后 | 只在事务内改写、前缀不动 | 只停用后缀区间，已建立前缀永不失效 |

## weave：把摘要当「受审计的产物」

关键机制（来源：`docs/principles.md`）：

1. **两级整理**（§1）：先做零模型调用的观测折叠——超过 4000 字符的非报错工具结果归档后替换为「头 300 + 尾 300 + 回查指引」；只有实测仍超线才进第二级摘要。实测重工具负载下摘要调用从 1 次降到 0 次。
2. **九节检查点 + 引擎确定性填充**（§3.2）：第 6 节「全部用户消息」由模型输出占位符，引擎按时间顺序把预算内（默认 32 条 / 4096 tokens）的用户原话逐字填入。模型不负责「记得用户说过什么」，引擎负责。
3. **通道隔离**（§3.2）：依据宿主事件通道而不是自然语言正则区分「真实用户指令」与「工具结果/网页/引用」。非用户通道统一包进 `<untrusted_reference>`；用户消息内部的引用用显式 XML 标签划界。这一点直接消灭了「工具输出里伪造的『用户已批准』被当成授权」这一类失效。
4. **要求审计**（§5.2）：对检查点做词汇覆盖（阈值 0.6）、数字与单位归一化、否定极性、双侧条件、上下限、传输方向、作用域比对；授权声明必须能按时间顺序重放到一条真实用户记录，否则 `CONSTRAINT_LOST` 阻断。
5. **双重严格缩小**（§5.1）：估算 tokens **与**规范化 UTF-8 字节都必须严格小于被替换区间，否则拒绝。这条防的是「加了原话和元数据后，检查点比原文还大」。
6. **增量与缓存**（§3.1、§2.3）：默认只折最新检查点之后的增量，保留检查点及之前的前缀逐字节不动；摘要请求在同路由下原样复用前缀，命中服务商缓存。
7. **事务保护**（§6）：`.rollback` 备份 + 单趟复制算 SHA-256 + `phase: committed` 分界线；宿主私有方法指纹不匹配时降级到公开 `Session.append(replace)`。

代价：整套审计规则是大量领域无关但复杂的启发式；作者自己也承认中文间接否定、未打标签的第三方摘录仍可能误判（§7）。摘要真值仍由模型产生，审计只能证明「没漏」，不能证明「没歪」。

## argp：把压缩做成「确定性剪枝 + 成本闸」

关键机制（来源：`ARCHITECTURE.md`）：

1. **原子模型**（§2）：对话拆成 U/A/R/X，只有 R（工具结果）可剪。散文永远不剪，焦点轮受保护。
2. **0 LLM 标签判定**（§2）：按实体标签（`document:<path>`、`command:<family>`、`errorcode:<CODE>`、`scope:<dir>`）与三条已发生事实判定——同文件更新读取、文件被改、当轮被引用；判不上的按新旧与体积排队。
3. **事务成对发射**（§3）：每个 `compaction/prune` 的 `shadowedRange` 必须与紧随其后的 surface `replace` 范围严格相等，否则宿主 resume 投影抛错。这是宿主强制的结构，不是设计偏好。
4. **两道闸**（§4.3）：散文浓缩只在「散文占声明窗 ≥50%」且「上下文 ≥0.8×声明窗」时触发；常规工具会话里 LLM 整场休眠。
5. **撞墙兜底**（§4.1）：默认不做本地估算拒发，交给 provider 400 `CONTEXT_WINDOW_EXCEEDED` 触发一次剪枝后重试。
6. **可撤销的遗忘**（§5）：被剪原文留在 append-only 日志，按标签或关键词逐字召回；召回预算单次 5% / 累计 10% 窗口。

代价：不留「检查点」，只有桩 + 指针。对「跨很多轮仍然有效的约束」没有专门保留机制——它依赖原日志可召回，而模型并不总会去召回（论文 §3.7 也观察到同一现象：模型不会自发使用恢复工具）。

## billion-context：把压缩做成「模型判断 + 内核簿记」

关键机制（来源：`paper/模型驱动的分层增量压缩-免训练多代上下文管理.md`）：

1. **职责切分**（§3.1）：「模型写摘要，内核负责其余一切编排」。流水线九段纯函数：assign-refs → sync-blocks → merge-blocks → prune → filter → hide-compress-calls → nudge-inject → emergency-truncate → render-refs。
2. **块是 LSM 树**（§3.2）：tier-1 折消息区间，tier-2 折块，tier-3 再折；`effectiveMessageIds` 传递性覆盖谱系，任意再压缩后仍能定位原文。生产数据：tier-1 常驻占 92%，tier-2+3 只占 8% 却承载 37% 历史。
3. **保护区在 filter 阶段硬执行**（§3.3），不在提示词里：压缩工具自身、近期区、最后一条用户消息、第一条用户消息永不可折。
4. **需求侧触发**（§3.4）：增速门控——上下文 ≥ 窗口下限比例（约 0.45）**且**自上次压缩以来增长 ≥ 50K 才注入 nudge；有效下限 22.5K。**nudge 从不告诉模型填充百分比**（模型会把 200K 窗口锚定在「20% 很健康」上而拒绝压缩）。
5. **拒绝权**（§3.7）：nudge 措辞是「保持精简的效率提示」，不是溢出警告；模型可拒绝。生产日志里 22% 的压缩发生在没有 nudge 的轮次（模型自发）。
6. **只压已消费增量**（§3.6）：每轮只折上次压缩以来的新增，于是质量风险、缓存失效、留存衰减、成本都变成 O(增量) 而不是 O(历史)。
7. **留存率指标**（§4.2）：定义 R(t) = 仍可恢复的历史比例。阈值式压缩每轮重摘要同一段历史 → R(k) ≈ ρ^k 几何衰减到 0；折叠每段只折一次 → R∞ = ρ₁ ≈ 1/8 恒正。这是「为什么折叠不会越压越差」的定量论证。
8. **decompress-to-file**（§3.2）：恢复原文写到文件而不是上下文，保住 KV 前缀。

代价：模型驱动意味着「压什么」不可复算——同一个会话重放两次可能折不同区间，审计与回归测试比确定性方案难得多。生产规模数据（174,327 次调用）来自作者自有部署，是纵向观察而非对照实验。

## 可迁移的五条结论

1. **确定性先行**：能在不调用模型的情况下解决的（超大工具输出、重复读取、被取代的编辑）绝不进 LLM 通道。weave 实测省掉 100% 摘要调用，argp 让 LLM 整场休眠——两条独立证据。
2. **模型写、代码守**：模型擅长判断「这段还需不需要」，不擅长保证「约束没丢」「数字没改」「授权是真的」。把语义判断留给模型，把结构判断写成代码，是被两个实现分别验证过的分工。
3. **只折增量，不重写前缀**：无论选哪种压缩，都要让已发送的前缀字节稳定。三份实现都为此付出了设计代价（weave 的增量检查点、argp 的事务成对发射、bili 的后缀停用）。
4. **触发看增速，不看填充率**：填充率是个模型无法用注意力校准的数字，告诉它只会让它误判。增速门 + 阶段边界才是与任务对齐的信号。
5. **恢复能力决定质量上限**：留存率 R∞ 恒正（bili）与归档回查（weave）说的是同一件事——只要原文仍在且指针可达，压缩就只是「暂时看不见」，不是「失去」。

## 明确不采纳的三条

1. **不采纳「摘要即记忆」**：三个实现都把摘要当成上下文的一部分；对我们这是双索引风险——摘要里的断言会与记忆库的断言各答一次，且摘要不可结算（无证据、无 falsifier）。设计上禁止记忆从检查点写入（AD-37）。
2. **不采纳纯阈值自动压缩**：bili 的论证成立（模型不感知、无法拒绝、无法选择），且与我们的「人格在场」定位冲突——一个从不询问就改写历史的同伴，不像同伴。
3. **不采纳本地估算拒发**：bili KDD #19 已用生产证据废除（本地窗口值常错，估算是乘性误差），交由上游 400 作为权威。

## 局限（诚实记录）

- 本侦察只读了三个仓库的实现文档与架构说明，**没有跑它们的基准**；对比表里的性能数字都来自各自作者的测量，不是本项目的复现结果。
- bili 的论文是作者对自己系统的纵向研究，样本是单一部署；用它论证「模型驱动更好」时可以，用它论证「比阈值好多少」时要打折。
- 三个仓库的宿主版本不同（weave/bili 面向 0.2.2-rc.x，argp 声明 0.2.0–0.2.x），宿主 API 细节可能已经变化；设计里凡依赖宿主 API 的地方都标了「以接缝实测为准」。
- 未检索第三方独立评测（时间预算优先给了源码阅读）。若要对外发布这套设计，应补一次独立基准。
